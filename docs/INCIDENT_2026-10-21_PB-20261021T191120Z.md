# Production incident — 2026-10-21 — pb-20261021T191120Z-532dc0

**Component:** pi-hermes-bridge v0.4.2 runner + Pi orchestrator
**Job:** `pb-20261021T191120Z-532dc0` (live gamewatch task, turn 1)
**Outcome:** silent hang ~33–52 minutes; manual tier-1 recovery restored
the Pi session within seconds. This incident is the design basis and the
regression case for the v0.5.0 stall watchdog
([STALL_WATCHDOG.md](STALL_WATCHDOG.md)).

## Observed evidence chain

| # | Signal | Observation |
|---|---|---|
| 1 | job status | `running`, runner systemd unit `pi-bridge-pb-20261021T191120Z-532dc0-t1` active, runner PID alive |
| 2 | Pi process | alive (turn's recorded `pi_pid` / `pi_start` identity matched) |
| 3 | Pi session JSONL | stale for ~33–52 minutes — no new entries at all |
| 4 | descendant CPU | ~0 across two `/proc` samples — no work being done |
| 5 | backend | local vLLM `192.168.2.123:8000/metrics`: `vllm:num_requests_running=0`, `vllm:num_requests_waiting=0` — Pi was not waiting on generation |
| 6 | process tree | stuck descendant: `bash -c ssh ... powershell -File capture.ps1` — an infinite-loop PowerShell script run as a **foreground tool command without any timeout** |

Root cause: Pi executed a long-running remote capture script as a
foreground tool call; the script loops forever, so the tool call never
returned, Pi sat waiting, the session produced no JSONL, and no component
in the chain (runner, wake, pi-lamp) considered the job anything but
"running".

## Manual recovery (what tier 1 was built from)

SIGTERM to **the verified descendant subtree only** (the `bash -c ssh ...`
command and its children), Pi itself untouched:

* the hung tool call returned an error to Pi within seconds;
* Pi continued reasoning **in the same session** (JSONL resumed,
  `pi_session_id` unchanged, context preserved);
* nothing else in the tree was disturbed.

## What v0.5.0 changes

The same evidence chain is now collected automatically every minute by
`pi-bridge watchdog tick`, confirmed multi-signal (never a single timer),
and tier-1-recovered automatically — bounded to 2 attempts, with a
`pi_bridge_stall` event to Hermes at the first attempt and
`needs_attention` + a user message if recovery does not take. See
`docs/STALL_WATCHDOG.md`; the synthetic reproduction of exactly this chain
(hanging bridge-owned descendant, no output, no CPU) is pinned in
`tests/test_watchdog.py` and requires: no reaction before the threshold,
confirmed detection, Pi NOT killed, only the descendant terminated, Pi
continuing, and the `recovered` state being recorded.
